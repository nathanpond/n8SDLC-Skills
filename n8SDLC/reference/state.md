# Local State Conventions (.n8/)

GitHub Issues/milestones are the source of truth for all planning. The tracked `.n8/` directory holds only what doesn't fit GitHub: configuration answers, the decision log, and free-form memories. Never duplicate issue content into `.n8/` — two sources of truth drift.

```
.n8/
├── config.yml       # project configuration and one-time answers
├── decisions.md     # append-only decision log
└── memory/          # free-form .md memories, one topic per file
```

## Committing state changes

Skills that write local state (`.n8/`, CLAUDE.md, README, templates) must land it on the remote — and once init installs the `main` ruleset, **direct pushes to main are rejected**. The rule is to batch the run's state edits into one short-lived branch (`n8/<skill>-state`), open a PR, and squash-merge it. Milestone execution doesn't need this, because it already works on milestone branches; every other skill that commits does.

The flow must never cost the user work. Their local `main` may carry commits they haven't pushed, and their working tree may hold edits that aren't the skill's:

```sh
git fetch origin
git rev-list --count origin/main..main   # must print 0
```

1. **Before cutting the branch,** that count must be 0. If it isn't, stop and show the user `git log --oneline origin/main..main`. Those are their unpushed commits. Ask whether to push them first (through their own PR) or to land the state on top of `origin/main` without them. Never fold them into the state PR, and never reset over them.
2. **Cut from the remote, stage by path:** `git switch -c n8/<skill>-state origin/main` (uncommitted edits come along), then `git add -- <each state file the run wrote>`, plus any uncommitted `.n8/` or CLAUDE.md state an earlier n8SDLC command left behind (e.g. `/n8-map`'s config write), which you name to the user in the report. Never use `git add -A` or `git add .`, because anything else in the working tree is the user's.
3. **After the squash merge:** `git switch main && git pull --ff-only origin main`. With step 1 passed, this always fast-forwards. If it refuses, something changed underneath, so report it and leave the repo as it is. Never fix it with `reset --hard`.

## config.yml

Created by `/n8-init`, extended by `/n8-roadmap`. Example shape (add keys as needed, keep flat and readable):

```yaml
version: 1
plugin_version: 0.7.0   # n8SDLC version whose project-side setup this project has; written by init, advanced only by /n8-upgrade
stack: dotnet            # dotnet | typescript | python | unity | flutter | <other>
initialized: 2026-08-27
wiki: enabled            # enabled | opted-out | unavailable
repo: nathanpond/example
visibility: public
deployment:              # /n8-plan's config surface reads targets, environments and ci.triggers, so keep these three keys
  targets: <platform(s) — e.g. "Cloudflare Workers", "GitHub releases">
  environments:          # every environment the project has, name → where it lives; omit stage with a one-line why in notes
    dev: <answer from roadmap Q&A>
    production: <answer — e.g. "tagged GitHub release with artifacts">
  notes: <how the app is deployed, hosting decisions, environments deliberately absent>
ci:
  provider: github-actions
  on_pr: [typecheck, lint, test]
  triggers:              # one row per trigger → environment
    - "push main → dev"
    - "push tag v* → production"
context7: installed      # installed | declined — when declined, skills skip context7 lookups without re-checking
security_findings: issues  # issues | advisories — how /n8-audit logs the project's own security findings
areas: [web, api, db, ci, infra, docs]  # the project's area:* labels, generated by init from its structure
baseline:                # existing projects only: what delivery already works. Shape and evidence rules in reference/delivery-baseline.md
  checked: 2026-09-29 @ 1a2b3c4
  established: ["merge gate: ruleset requires ci/test; PR #140 ran it green"]
  gaps: ["environment gate: production has no protection rules"]
  not-wanted: []
  observed-guards: []    # guard tests/settings seen by /n8-map; /n8-roadmap classifies them against confirmed invariants
```

Skills read `wiki:` before touching wikis. `opted-out` means the user said no — skip all wiki work silently, don't re-ask. `enabled` can still mean *uninitialized*: the wiki git repo 404s until someone creates the first page in the web UI (there is no API for this). On a 404, skip the wiki write, remind the user of the one-time manual step, and continue — never fail the skill over it.

## decisions.md

Append-only log of every decision made during planning and (especially) execution. During autonomous execution the user isn't watching — this log is how they audit what happened. Record real decisions (choices between alternatives, assumptions made, deviations from plan), not routine actions.

Format — one `##` section per skill run, entries appended chronologically:

```markdown
## /n8-exec M1 — 2026-08-27

- **Decision:** Used SQLite for local dev database instead of running Postgres in Docker.
  **Why:** Plan specified "local relational DB" without naming one; SQLite needs no daemon and the ORM abstracts the difference. Low cost if wrong.
  **Issue:** #14
```

After execution completes, the exec skill displays all decisions from its run to the user.

### Ad-hoc entries (the drift ledger)

Changes made outside the n8SDLC commands that deviate from planned issues get an `## Ad-hoc` section — this is the primary evidence `/n8-replan`, `/n8-exec`'s preflight, and `/n8-stat` use to detect stale plans. `/n8-init` puts a standing instruction in the project's CLAUDE.md so any agent session writes these.

```markdown
## Ad-hoc — 2026-08-27

- **Change:** Auth provider switched from Google to Okta.
  **Why:** Company standardized on Okta for SSO.
  **Affects:** M4 (auth stories), M6 (admin roles) — plans may be stale.
```

When `/n8-replan` processes an entry, it appends `— reconciled by /n8-replan <date>` to it so drift checks stop flagging it. Unreconciled entries + unexecuted planned milestones = suspected drift.

## memory/

Free-form markdown memories — anything worth remembering across sessions that isn't planning state: quirks of the deployment target, user preferences discovered mid-project, external service credentials *locations* (never the credentials themselves), lessons learned. One topic per file, short kebab-case names. Check for an existing file on the topic before creating a new one.
