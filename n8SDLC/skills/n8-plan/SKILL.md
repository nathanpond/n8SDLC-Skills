# /n8-plan — Milestone Planning

Plan milestones down to the level where execution needs to ask **nothing**. The bar: an agent with no access to the user must be able to implement every story from its issue alone — and §3 tests that bar with a fresh agent before anything is filed, because you cannot judge it yourself. Any question you don't ask now becomes a blocker during `/n8-exec`. Planning is the phase that decides whether execution is autonomous or a series of stalls; spend the questions here.

Read `${CLAUDE_PLUGIN_ROOT}/reference/github.md`, `${CLAUDE_PLUGIN_ROOT}/reference/state.md`, and each stack file in `${CLAUDE_PLUGIN_ROOT}/reference/stacks/` that `.n8/config.yml` names.

## 1. Resolve targets

Parse the argument: a single milestone (`M0`), a comma list (`M1,M2`), or `*` (all open milestones not yet planned — a milestone counts as planned when it has stories assigned). Match milestones by `M<N>:` prefix, never full title. An explicit target that is the Audit milestone (titled `M<N>: Audit`) gets "Audit takes stories only from `/n8-audit`" and stops. Any other milestone that already has stories is **re-planned**, not skipped when named explicitly: its existing stories are the starting slate, the enumeration below runs against them, and only the delta is presented. **The Audit milestone is exempt from `*` and counts as planned once its description carries an `emphases:` line without `(provisional`** (written by the whole-project analysis below) — it gets stories from `/n8-audit` findings, never pre-created ones. Requirements:

- `/n8-roadmap` must have run (epics + milestones exist); otherwise say so and stop.
- Plan milestones in order. If the user asks for M2 but M1 is unplanned, say so and put "proceed anyway?" at the head of round one — later plans usually depend on earlier decisions, and nothing is created before the answer.

## 2. Interrogate per milestone

The interrogation is a fixed sequence of turns; the names below are used throughout. **Round one** (outcomes, tier, shape questions, triage proposals), **round two** (the executor simulation's guesses, always sent), the **scope question** (after the coverage check, with the slate — only when something is uncovered), and the **approval gate**. Conditional questions attach to a round: triage proposals and "M1 is unplanned — proceed?" join round one; duplicate-check questions ("extend #N or new?") join round two. Nothing is presented for approval before every turn that applies has happened.

**Housekeeping first, no user turn.** Sweep `needs-triage` issues (quick captures from `/n8-file` and discovered-work filings) and draft a proposal for each — story in a targeted milestone, fold into an existing issue's AC, or wait; triage is planning's job. Check the project invariants in CLAUDE.md on **every** milestone: each invariant whose line says `enforce: test` and carries no `guard:` annotation needs a story creating its **executable guard** (a test or build setting that fails when the invariant is breached — package-count test, public-API snapshot, warnings-as-errors). The guard's *subject* exists once the guard could fail on a real breach today — an empty API snapshot that any first endpoint would break exists at M0. The guard lives in the milestone where that first becomes true: M0 when M0's epic includes the build or test project, otherwise the CI milestone; if that home is already closed, the milestone being planned. A guard deferred to a later milestone is annotated `guard: deferred → M<N>` now; an unguarded invariant whose home is closed and carries no such line was forgotten — plan it now and log the miss in `.n8/decisions.md`. What the founder's own invariant *means* ("public API surface": HTTP contract, or assembly types?) is a founder question for round one. After creation, annotate `guard: #N (planned)`; `/n8-exec` rewrites it to `(merged)` when the guard code lands — the invariant is enforced only from then.

**Outcomes.** Before any question or story, write five to ten user-observable outcomes — what a person can do, see, or rely on when this milestone closes that they cannot today — one per line, no artifacts ("CI blocks a PR whose tests fail" is an outcome; "GitHub Actions configured" is not). They are not the *definition of done* in `reference/github.md`, which is the same mechanical close condition for every milestone; outcomes are what this milestone alone adds. For a milestone with an external surface (below), the outcomes are the cross-cutting truths the item list can't express — rejection of the unsupported, observability, persistence across restart; for a config surface they are what the founder will notice — what blocks a merge, what happens when a deploy fails, what they never do by hand. The item list is the coverage instrument: every item traces to a story, every outcome traces to a story, and a story that owns items need not trace to an outcome. Guard stories and spikes are listed under the map as `HOUSEKEEPING: <story>` and are exempt from both. The outcomes head round one's message, ending with the verbatim *"When this milestone is done, is this everything you expect to be true? What's missing?"*; the confirmed list is written under `## Outcomes` in the milestone PATCH (§3), each line ending `→ #<issue>`, and an outcome with no story is a coverage finding.

**The surface, counted before round one and mapped after drafting.** Every milestone has one, and the count is what the tier and scope questions reflect back, so it is derived in a way two planners would repeat.

- *External surface* (a specification's element set, a list of endpoints, a set of pages): the roadmap's `coverage-claim` block names the source, its locator, the tier, the tables, and — in `covers:` and `remainder:` — which part of the claim this milestone delivers. Open the locator; if it cannot be read, stop and say so — never enumerate from memory. Extract the tables' text and hand that to the coverage checker, which otherwise stops the same way. Resolve each table name to its number or section and give it a **role**: the *tier list* (the one table or section that says which elements the tier includes) or a *universe* (a table listing everything the source defines for some element class); correct the block's numbers in the PATCH if the source disagrees. Only the tier is a founder question — if the block lacks it, ask verbatim in round one: *"<source> has tiers (<list them>). Which does this milestone target?"*; a missing universe table for a noun in the milestone title is a docs lookup you do yourself. **Scope:** the tier-list rows in play are those `covers:` names; rows the block assigns elsewhere are `REMAINDER: <items> → M<N>` and not in N; if `covers:` and `remainder:` together do not name every in-tier row, stop: list the unassigned rows, propose a home for each (this milestone or a named later one), say that the block splits by something other than rows if `remainder:` names a milestone without naming rows, and tell the user the roadmap block must be corrected before `/n8-plan M<N>` is re-run — the planner never amends `covers:` itself. **Grain:** one in-scope row of the tier list; a parenthetical variant on a row is its own item; where a row names an element whose variants a universe table lays out as a matrix (event type × position), *position* means the universe table's column, each cell whose type the tier list names for that column is an item, and a row that does not distinguish sub-positions names only the first column of its own position group (top-level for start rows, catching for intermediate rows, interrupting for boundary rows) — the rest are `OUT-OF-TIER`. Never split below that, never merge above it. `OUT-OF-TIER:` lines are the universe tables' entries the tier list omits.
- *Config-derived surface* (an infrastructure or CI milestone): the roadmap's own answers are the source, and the grain is this list, stated once — the header block repeats it verbatim. One item per `trigger → environment` row under `ci:` in `.n8/config.yml` (`deployment.targets` is the platform; the row's right-hand side is an environment, and one named by a trigger but absent from `deployment.environments` is a config gap to ask about in round one). One item per environment under `deployment.environments` that no trigger names, written `→ ?`. One **merge gate** item (what blocks a PR). One **environment gate** item (approval, protected tag, rollback) for each stage or production environment — a gate with no story is `→ ?`. One item per unguarded invariant; a guard and a day-one entry for the same policy are one item, owned by the guard. One item per day-one entry, as defined in `${CLAUDE_PLUGIN_ROOT}/reference/delivery-baseline.md` → *The items* (the stack file's `## CI` chain steps that apply, plus secret scanning and dependency updates). When `stack:` names more than one buildable, one item per deployable × environment, unless round one settles that they ship as one artifact. When M0 and a CI milestone would both own a trigger, gate or day-one row, it belongs to the milestone whose epic the roadmap assigned it to — so `Source:` names both milestones' epics. "M0 has no surface" is how M0 ships with two environments of three.

The map's header block is, for an external surface, `Source: <locator>; tier: <tier> (<section>); tier list: <table/section>; universe: <table> (<columns>); grain: one in-play tier-list row, parenthetical variant = item, matrix cell by column, first column of the position group when undistinguished; N=<n>, K=<k>`; for a config surface, `Source: .n8/config.yml (ci:, deployment:, stack:), CLAUDE.md, <stack files>, the epics of M0 and this milestone; grain: <the config-surface list above, verbatim>`. Count N from the header before round one; a `DESCOPED:` item leaves N and joins K's complement — the scope and gate sentences count in-scope items after descoping, so "all N covered" is never false by the descoped ones. Draft the map as soon as the slate exists, before the duplicate check (the review artifact shows it) — `<item> → S<n>`, `<item> → #<issue>` where the duplicate check resolved it to an existing issue, `<item> → ?` for an item no story owns yet, `<item> → S1, S6` when two stories each deliver a named part — and write it to the milestone description with `#<issue>` throughout in one PATCH after creation (immediately, on a re-plan that created nothing). Other line kinds: `OUT-OF-TIER: <items> — not in the <tier> tier, per the coverage claim`; `DESCOPED: <items> — "<user's reply, quoted>"` for in-scope items the milestone will not do — written the moment the user excludes something, in round one or later, and never listed as uncovered again; `IN-BY-REQUEST: <item> — "<user's reply, quoted>"` for an out-of-tier item the user pulls in, which also amends the roadmap's block in the same PATCH; `ESTABLISHED: <item> — <evidence>` on a config surface, for an item listed under `baseline.established` in `.n8/config.yml`, copied with its evidence. It leaves N like `DESCOPED:`, and gets no story, because the project already has it. Re-run its evidence command before writing the line: an item that no longer passes is a gap, and gets a story. On a config surface, an answer that changes the config — preview becomes a fourth environment, a trigger for stage, a new row the user asks for — is written to `.n8/config.yml` and landed in §5 with the guard annotations, and the map records the row as the config now states it. `/n8-verify` reads these lines.

**When a milestone opens with a survey or inventory story, check what that story enumerates.** If its source is a proxy for the thing being claimed, the survey reads as complete while being structurally incapable of finding what the proxy omits — a modeler's node palette standing in for a specification silently excludes every construct expressed as a marker on an element rather than as a palette entry. **When the answer is "proxy": replace the source in that story's acceptance criteria with the defining one and re-run the enumeration before slicing anything.** Don't keep the survey and add a caveat — a survey with the wrong source is not partially right.

**Shape-derived questions.** For each milestone, study its epics and phases, then ask everything execution would otherwise have to guess. **Derive question areas from the shape of what's being built, never generic categories**: something users SEE → states, interactions, visual behavior; something users CALL → contracts, responses, errors; something users RUN → invocation, flags, output; something being ORGANIZED → criteria, grouping, exceptions; something that DEPLOYS or GATES → what puts each deployable on each environment, what blocks a merge, whether the tag or merge is itself the production approval or a confirm step follows, which set of secrets each environment and each preview reads, what happens when a deploy fails or must be rolled back. (`secrets: wrangler` in config answers where secrets are stored, not which set a preview reads — the skip rule does not skip it.) ("User authentication" → session handling, error responses, multi-device policy, recovery flow — not "UI/UX/Behavior".) Verify library, API, and build/CI tooling claims — action names and current majors included — via context7 when available (skip when config says `context7: declined`; for GitHub Actions the lookup is `gh api repos/<owner>/<action>/releases/latest --jq .tag_name`) — plans built on stale docs produce broken code.

Respect the role split: **the user is the founder, you are the builder.** Ask them how it should work, look, and feel, and what's essential vs. nice-to-have — phrased in terms they can observe, with any platform noun explained in one clause ("a preview — a throwaway copy of the app for that one PR"). Never ask them about codebase patterns, technical risks, or implementation approach — read the code and docs for those. Two capture rules while questioning:
- **Scope creep deflects losslessly:** an answer that adds a new capability ("does this clarify what's in scope, or add something that could be its own story?") gets captured via `/n8-file`-style issues — the one kind of issue created mid-discussion — not folded in silently or dropped.
- **Delegation gets recorded:** every "you decide" answer lands in the story's **Claude's Discretion** section, marked `(user)`; the planner's own calls from round two land there marked `(planner)`. Either way it is the map of where autonomous execution may improvise without raising a blocker.

**Round one** is one batched message: the outcomes, the tier question if it fires, the triage proposals, and the shape-derived questions — skipping any whose answer is already in `.n8/config.yml`, existing issues, the codebase, or an outcome in the same message (an outcome the user rejects reopens its question). Draft the stories from the answers. Round two is the executor simulation in §3; it exists only because round one's answers shaped stories that can be simulated, and it is always sent. One round is not enough — the questions worth asking about M0 are the ones an executor would trip over, and they only become visible once there are stories to execute.

## 3. Create stories and subtasks

Every story body carries the full template from `reference/github.md`, including two blocks that make verification structural rather than trust-based:
- **Must-haves, derived goal-backward:** state the user-observable truths first, then the artifacts that realize them, then the key links where stubs hide. "Task completion ≠ goal achievement" — a "create chat component" task can complete while the component is a placeholder; the truths are what verify actually checks.
- **Demo** — a concrete ~60-second user script — for stories a human will verify (user-facing flows, anything with manual verification steps); a story whose every AC the agent can exercise itself carries `Demo: none — agent-verifiable` instead (anything needing a human approval or an external side effect the agent cannot trigger keeps a Demo); `/n8-verify --auto` derives its checks from the AC and must-haves instead.

**Test plans assert the complement.** A test that checks only what *should* happen cannot distinguish "the feature works" from "the code does this unconditionally" — the distinguishing evidence is almost always what should *not* have happened, or what should have *stopped*. Asserting that an interrupting timer's alternate path ran, without asserting the task was **cancelled**, passes for a non-interrupting timer — the opposite feature. Asserting a scoped broadcast woke a same-scope listener, without asserting an out-of-scope listener did **not**, omits the entire feature. Asserting a permitted user gets through, without asserting an unpermitted one is **refused**, is the only half that detects a missing gate in a harness that defaults authorization off. So: where a story's correctness depends on something not happening, or on something being cancelled, superseded or refused, the test plan says so explicitly — assert the observable consequence one step further out than feels necessary. Where a test exists to prove a fix, the test plan **says to run it against the pre-fix state first and watch it fail** — a test that passes before the change does not test the change, and execution will not think to check unless the plan says so. Any mechanical guard states what it does *not* cover.

**Checks before filing**, in this order: draft the map → duplicate check → executor simulation → round two → fold answers and re-simulate → coverage check → present with the scope question if needed → approval gate.

- **Executor simulation — the bar, tested.** The bar is that an agent with no access to the user can implement every story from its issue alone; you cannot judge that, because you know what you meant. After the duplicate check, for each drafted story spawn a fresh `general-purpose` subagent (never `fork`) with the story body, its epic's body, the slate's titles, the repo path, `.n8/config.yml` and CLAUDE.md, and this brief verbatim: *"You will implement this issue with no one to ask. Read only the issue, its epic, the listed sibling titles, the config, the codebase, and — where the milestone has an external surface — the source at the coverage claim's locator. List every decision you would have to make that the issue does not settle — a value, a shape, a policy, a choice between two defensible approaches. A decision another listed story settles is not yours. One line each. Do not implement anything."* A story whose first-pass list comes back empty is suspicious, not done — re-run it with this brief instead (an empty second-pass list is accepted): *"Quote the acceptance criterion you would implement first and the file you would open first, then list every decision the issue does not settle."* An empty list with a correct quote is accepted. Before routing, merge guesses that recur across stories: an engine-wide decision is routed once, its `(planner)` line lives in the story created first, and the others carry `see S<n>`. **Route each guess**: a decision about how the product behaves for a user, or about what the founder's own invariant means, is a round-two question; a decision about how to build it is a `(planner)` line in that story's Claude's Discretion block or a tightened AC. **Round two** is one message: the questions, every Discretion line the plan now carries, the duplicate-check questions, and the verbatim close *"Anything in the discretion list you'd rather decide yourself? If so, state your call in this reply."* — any reply is the acknowledgment, and a call stated there becomes a `(user)` line. Fold the answers in, re-simulate the stories whose bodies changed **once**, and put that pass's build decisions straight into Discretion as `(planner)`; its product-facing guesses go into the gate message under *"decided by the planner unless you say otherwise"*. There is no round three. Stories added later (after the scope question) get the same single simulation before the gate; their product-behaviour guesses are appended to the gate message as questions, and the go either answers them or sends the story back. Both passes are posted under `## Executor simulation` in the milestone PATCH.
- **Coverage — a check on the *set*, and not one you can run yourself.** Does this story set discharge what the milestone *claims*? The three checks below are all per-story, and a plan can pass every one of them while covering a fraction of its milestone. The scope backstop only ever splits a story that exists; it can never notice a missing one. After round two's edits, hand a **fresh subagent** the source — the locator or extracted table text and the tier for an external surface; the `ci:`/`deployment:`/`stack:` blocks, the unguarded invariant lines and the stack files' day-one entries verbatim for a config surface — the map's header block, the full map (OUT-OF-TIER, REMAINDER, DESCOPED and IN-BY-REQUEST lines included), the outcomes with their `→ S<n>` links, and the reconciled story bodies, and ask: which in-scope items are missing from the map, which map items are `→ ?`, which `## Outcomes` lines no story traces to, how many items each story owns and, for each owned item, to quote the acceptance criterion that delivers it — an AC that merely mentions the item does not. Its list is the artifact, written under `## Coverage check` in the milestone PATCH (final run). A story owning more items than it has acceptance criteria is split until each piece meets the backstop — one omnibus story can give every item an owner and cover nothing. An item whose AC the checker rejected is `→ ?` from here on.
- **Present the map and slate.** When any item is `→ ?`, ask the **scope question** verbatim, naming the uncovered items — the first sentence only when a totalising word exists, quoted from the coverage claim if it has one, else the title: *"The <claim|title> says '<word>'. Of the <N> in-scope items in <source> at the <tier> tier, the stories cover <M>. Uncovered: <items>. Name the ones to leave out, or say 'all in'. <K> more are outside the <tier> tier — name any to pull in."* For a config surface the sentence is *"Of the <N> items derived from `.n8/config.yml`, CLAUDE.md and the stack files, the stories cover <M>. Uncovered: <items>. Name the ones to leave out, or say 'all in'."* — no tier clause. When nothing is uncovered, there is no scope turn: a totalising milestone's gate message carries one line — *"All <N> in-scope items are covered; <K> more are outside the <tier> tier — name any to pull in."* — and a pull-in named there is handled like a scope-question reply, after which the gate is shown again. DESCOPED items are never listed as uncovered. Write `DESCOPED:` and `IN-BY-REQUEST:` lines from the reply's words; for the rest, tighten the owning story's AC or add a story, simulate any new story once, re-run the checker on every story whose body changed; then the approval gate.
- Every key link has an *owning task* — wiring mentioned nowhere is wiring that won't exist ("Chat.tsx created but nothing wires it to /api/chat" is the classic miss).
- Every truth is user-observable — "JWT library installed" is not a truth; "user can log in" is.
- Scope backstop: a story needing more than ~8 files or that can't be described in three or four checkable criteria is split, and split again, until each piece fits.

**The approval gate.** Show a compact review artifact — the map (with `S<n>` ids) first where one exists, then one line per issue: `S<n> — title — labels — new | extends #N — one-line outcome`, marking which are epics/spikes and what depends on what. Enough to judge the slicing without reading full bodies. Never create issues speculatively mid-discussion (the `/n8-file` captures in §2 are the one exception), and never skip the gate because the plan seems obvious.

On the user's go, create:

- **Story** — `feature` (or `bug`/`security`/`performance`/`documentation`) label plus exactly one `area:*` label, story body template: the *what*, testable acceptance criteria, and a **test plan** naming the specific automated tests that will prove it. If an AC cannot be written as something testable, the story is too vague — split it or ask; an AC that demonstrates a *failure* case ("a warning fails CI") must also say how to synthesize that failure, or execution will have to invent one; if the work genuinely can't be demonstrated by a test, the story must say so explicitly and state how it will be checked instead. **Slice vertically, not horizontally**: one story per shippable slice cut through every layer together ("show the games list end to end" beats table + endpoint + component as three stories), because only the vertical slice can be verified on its own — and per-story verification is how `/n8-verify` works. Size stories so one fits in a single working session — oversized stories are where autonomous execution stalls. Titles are outcomes phrased as verbs ("Serve the games list from the DB", not "Games API"). Every story that changes behavior gets tests in its own scope — the milestone's definition of done includes all tests passing, so untested stories are incomplete stories. Assign to the milestone. Attach as a **sub-issue of its epic**.
- **Spike** — when planning hits a question that can't be answered by asking the user or reading docs (a technology choice needing a prototype, an unknown integration), don't guess and don't stall: file a `spike`-labeled issue, time-boxed, sequenced before the stories that depend on its answer. A spike closes with a **decision comment** and follow-up stories, never with code.
- **Subtask** — `subtask` label, only where the *how* genuinely needs prescribing (specific files, patterns, gotchas, sequences). Attach as a sub-issue of its story. Don't manufacture subtasks for self-evident implementations.
- **Dependencies** — wire `blocked_by` relationships (native flags, body-line fallback per `reference/github.md`) wherever order matters; ordering lives in the graph, not in prose. Execution follows these strictly.
- **Epic AC patterns** worth using where they fit: "each child implemented *or closed with the reason it will not be*" (so an epic can complete honestly without every idea surviving); a docs/wiki-update obligation tied to children landing; an explicit "nothing here weakens the project invariants" clause. For epics with many candidate children, tier them by leverage (highest return → hygiene), one line of justification per child — it makes descoping decisions legible later.
- **Create in dependency order** (blockers before dependents) so `--blocked-by` and body cross-references carry real numbers; where a forward reference is unavoidable, fix it afterward with one `gh issue edit --body-file` pass — never leave `#TBD` behind.
- **The milestone PATCH**, one edit after creation, keeps the roadmap's goal, coverage-claim block and definition of done in place and appends, in order: `## Outcomes` (each `→ #<issue>`); the coverage-claim block (external surfaces only), amended only for IN-BY-REQUEST or corrected table numbers; the map with its header block; the phase list restructured to the final story set, with a note that roadmap's coarse phases were re-sliced; `## Coverage check` (final run); `## Executor simulation` (both passes). Nothing else edits the description; `reference/github.md` lists the same additions.

## 4. Whole-project analysis (after all targeted milestones are planned)

Step back and analyze the full plan for what the roadmap couldn't see. Everything written here is **provisional** — marked `(provisional — after M<N>)` — unless this run planned the highest-numbered feature milestone *and* every lower one already has stories; only then is it written without the marker, and an analysis that finds no special emphases writes `emphases: none beyond the default suite` so the Audit milestone (titled `M<N>: Audit`, and never a valid explicit target) still counts as planned.

- **Specialized audits:** does the app's functionality raise specific concerns — user-generated content (security/XSS), payments (authorization), public-facing UI (508), heavy data processing (performance)? Suggest which `/n8-audit` areas deserve emphasis and record them in the Audit milestone description.
- **Project-specific skills:** would a purpose-built skill pay for itself — e.g. a "plugin-creator" skill for an app with a plugin system, a content-format skill, a deployment runbook skill? Suggest candidates and offer to build approved ones now via `/n8-skill`.
- **Gaps:** cross-milestone integration risks, missing stories, test coverage holes. Fix with the user's approval.

Log notable planning decisions to `.n8/decisions.md`.

## 5. Commit and report

Land any local state edits (`.n8/decisions.md`, CLAUDE.md invariant markings) per `reference/state.md`'s "Committing state changes" — the main ruleset blocks direct pushes.

Per milestone: story count, subtask count, dependency chains, test coverage summary. Then the analysis outcomes (audit emphases, suggested skills). Finish with the next step — `/n8-plan <next unplanned>` if milestones remain unplanned, otherwise execution of the lowest planned-but-unexecuted milestone (mention `/n8-exec *` in the sentence above as the run-everything alternative):

> ➡ Next: /n8-exec M1

**End on the Next line.** The reply's final line is `➡ Next: /n8-exec M1` (an example — substitute the real command and arguments): one recommended command, alone on the line, nothing after it. The why and any alternatives go in the sentence above it, never appended to it. Claude Code's prompt suggestion reads the transcript; a bare, final, unambiguous command is what lets the user accept it with Tab.
