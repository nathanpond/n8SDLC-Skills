# /n8-plan — Milestone Planning

Plan milestones down to the level where execution needs to ask **nothing**. The bar: an agent with no access to the user must be able to implement every story from its issue alone. Any question you don't ask now becomes a blocker during `/n8-exec` — and an execution-time question is a planning failure.

Read `${CLAUDE_PLUGIN_ROOT}/reference/github.md`, `${CLAUDE_PLUGIN_ROOT}/reference/state.md`, and the stack file in `${CLAUDE_PLUGIN_ROOT}/reference/stacks/` matching `.n8/config.yml`.

## 1. Resolve targets

Parse the argument: a single milestone (`M0`), a comma list (`M1,M2`), or `*` (all open milestones not yet planned — a milestone counts as planned when it has stories assigned). Match milestones by `M<N>:` prefix, never full title. An explicit target that is the Audit milestone (titled `M<N>: Audit`) gets "Audit takes stories only from `/n8-audit`" and stops. Any other milestone that already has stories is **re-planned**, not skipped when named explicitly: its existing stories are the starting slate, the enumeration below runs against them, and only the delta is presented. **The Audit milestone is exempt from `*` and counts as planned once its description carries an `emphases:` line without `(provisional`** (written by the whole-project analysis below) — it gets stories from `/n8-audit` findings, never pre-created ones. Requirements:

- `/n8-roadmap` must have run (epics + milestones exist); otherwise say so and stop.
- Plan milestones in order. If the user asks for M2 but M1 is unplanned, point it out and ask whether to proceed anyway — later plans usually depend on earlier decisions.

## 2. Interrogate per milestone

First, sweep `needs-triage` issues (quick captures from `/n8-file` and discovered-work filings): for each, propose with the user whether it becomes a story in a targeted milestone, folds into an existing issue's AC, or waits. Triage is planning's job — captures shouldn't accumulate.

Check the project invariants in CLAUDE.md on **every** milestone: each invariant whose line says `enforce: test` and carries no `guard:` annotation needs a story creating its **executable guard** (a test or build setting that fails when the invariant is breached — package-count test, public-API snapshot, warnings-as-errors). The guard lives in the milestone where its *subject* first exists — a storage-format compat fixture can't precede the format, so that guard is planned with the storage milestone, when that milestone is planned; M0 or the CI milestone hosts the ones that can run from day one. If the milestone that should host a guard is already closed, the guard goes in the milestone being planned. A guard deferred to a later milestone is annotated `guard: deferred → M<N>` now, so the next planner can tell deferred from forgotten. After creation, annotate `guard: #N (planned)`; `/n8-exec` rewrites it to `(merged)` when the guard code lands — the invariant is enforced only from then.

**Enumerate the countable surface before slicing it.** Where a milestone's scope is enumerable — a specification's element set, a list of endpoints, a set of pages — enumerate it from the **defining source**, never from what the project already has: a vendor compatibility matrix, an existing UI palette, or a library's coverage table each enumerate what somebody already built, and a plan drawn from one inherits its omissions. The roadmap's `coverage-claim` block names the source, its locator, the tier, the tables, and — in `covers:` and `remainder:` — which part of the claim this milestone delivers. Open the locator; if it cannot be read, stop and say so — never enumerate from memory. Resolve each table name to its number or section and give it a **role**: the *tier list* (the one table or section that says which elements the tier includes) or a *universe* (a table listing everything the source defines for some element class). Only the tier is a founder question — if the block lacks it, ask verbatim: *"<source> has tiers (<list them>). Which does this milestone target?"*; a missing universe table for a noun in the milestone title ("gateway") is a docs lookup you do yourself and add to the block. **Scope:** the tier-list rows in play are those the block's `covers:` names; rows the block assigns elsewhere are written as `REMAINDER: <items> → M<N>` and are not in N. **Grain:** one in-scope row of the tier list; a parenthetical variant on a row is its own item; where a row names an element whose variants a universe table lays out as a matrix (event type × position), each cell whose type the tier list names for that position — in a parenthetical or in prose — is an item, and a row with no such naming is one item. Never split below that, never merge above it. `OUT-OF-TIER:` lines are the universe tables' entries the tier list omits. The map's first line records each table's number and role plus the grain, so two planners produce the same count and `/n8-verify` can re-derive it. Draft the map in the review artifact with the slate's ids — `<item> → S<n>`, `<item> → #<issue>` where the duplicate check resolved it to an existing issue, or `<item> → ?` for an item no story owns yet; on a re-plan, existing stories keep their `#<issue>` and only the delta is new. Write it to the milestone description with `#<issue>` throughout in one PATCH after creation — immediately, on a re-plan that created nothing — together with the phase list and, under `## Coverage check`, the checker's list verbatim; that PATCH is the only description edit. Other line kinds: `OUT-OF-TIER: <items> — not in the <tier> tier, per the coverage claim`; `DESCOPED: <items> — "<user's reply, quoted>"` for in-scope items the milestone will not do; `IN-BY-REQUEST: <item> — "<user's reply, quoted>"` for an out-of-tier item the user pulls in, which also amends the roadmap's block in the same PATCH. `/n8-verify` reads these lines.

**When a milestone opens with a survey or inventory story, check what that story enumerates.** If its source is a proxy for the thing being claimed, the survey reads as complete while being structurally incapable of finding what the proxy omits — a modeler's node palette standing in for a specification silently excludes every construct expressed as a marker on an element rather than as a palette entry. **When the answer is "proxy": replace the source in that story's acceptance criteria with the defining one and re-run the enumeration before slicing anything.** Don't keep the survey and add a caveat — a survey with the wrong source is not partially right.

For each milestone, study its epics and phases, then ask everything execution would otherwise have to guess. **Derive question areas from the shape of what's being built, never generic categories**: something users SEE → states, interactions, visual behavior; something users CALL → contracts, responses, errors; something users RUN → invocation, flags, output; something being ORGANIZED → criteria, grouping, exceptions. ("User authentication" → session handling, error responses, multi-device policy, recovery flow — not "UI/UX/Behavior".) Verify library and API claims via context7 when available (skip when config says `context7: declined`) — plans built on stale docs produce broken code.

Respect the role split: **the user is the founder, you are the builder.** Ask them how it should work, look, and feel, and what's essential vs. nice-to-have. Never ask them about codebase patterns, technical risks, or implementation approach — read the code and docs for those. Two capture rules while questioning:
- **Scope creep deflects losslessly:** an answer that adds a new capability ("does this clarify what's in scope, or add something that could be its own story?") gets captured via `/n8-file`-style issues, not folded in silently or dropped.
- **Delegation gets recorded:** every "you decide" answer lands in the story's **Claude's Discretion** section — an explicit map of where autonomous execution may improvise without raising a blocker.

Batch questions sensibly rather than dribbling them one at a time. Skip questions whose answers are already in `.n8/config.yml`, existing issues, or the codebase.

## 3. Create stories and subtasks

Every story body carries the full template from `reference/github.md`, including two blocks that make verification structural rather than trust-based:
- **Must-haves, derived goal-backward:** state the user-observable truths first, then the artifacts that realize them, then the key links where stubs hide. "Task completion ≠ goal achievement" — a "create chat component" task can complete while the component is a placeholder; the truths are what verify actually checks.
- **Demo** — a concrete ~60-second user script — for stories a human will verify (user-facing flows, anything with manual verification steps); a story whose every AC the agent can exercise itself carries `Demo: none — agent-verifiable` instead; `/n8-verify --auto` derives its checks from the AC and must-haves instead.

**Test plans assert the complement.** A test that checks only what *should* happen cannot distinguish "the feature works" from "the code does this unconditionally" — the distinguishing evidence is almost always what should *not* have happened, or what should have *stopped*. Asserting that an interrupting timer's alternate path ran, without asserting the task was **cancelled**, passes for a non-interrupting timer — the opposite feature. Asserting a scoped broadcast woke a same-scope listener, without asserting an out-of-scope listener did **not**, omits the entire feature. Asserting a permitted user gets through, without asserting an unpermitted one is **refused**, is the only half that detects a missing gate in a harness that defaults authorization off. So: where a story's correctness depends on something not happening, or on something being cancelled, superseded or refused, the test plan says so explicitly — assert the observable consequence one step further out than feels necessary. Where a test exists to prove a fix, the test plan **says to run it against the pre-fix state first and watch it fail** — a test that passes before the change does not test the change, and execution will not think to check unless the plan says so. Any mechanical guard states what it does *not* cover.

**Checks before filing** (on the whole batch, after the duplicate check, before presenting):
- **Coverage — a check on the *set*, and not one you can run yourself.** Does this story set discharge what the milestone *claims*? The three checks below are all per-story, and a plan can pass every one of them while covering a fraction of its milestone — a well-formed eighteen-story plan once covered a fraction of its milestone, and nothing in the process registered it. The scope backstop only ever splits a story that exists; it can never notice a missing one. Because you wrote these stories, you are the one reader who cannot check their coverage: after the duplicate check (so it sees `→ #N` for extensions and the merged AC), hand a **fresh subagent** the source locator, the tier, the table numbers with roles, the grain, the full map (OUT-OF-TIER, DESCOPED and IN-BY-REQUEST lines included) and the reconciled story bodies, and ask: which in-tier items are missing from the map, which map items are `→ ?`, how many items each story owns and, for each owned item, to quote the acceptance criterion that delivers it — an AC that merely mentions the item does not. Its list is the artifact, written under `## Coverage check` in the milestone PATCH. A story owning more items than it has acceptance criteria is split until each piece meets the backstop — one omnibus story can give every item an owner and cover nothing. An item whose AC the checker rejected is `→ ?` from here on. **Then present the map and slate, and whenever any item is `→ ?`, or the title or the coverage claim is totalising** ("full", "complete", "all", "every", "conformant"), ask verbatim, naming the uncovered items — the first sentence only when a totalising word exists, quoting it from wherever it sits: *"The <title|claim> says '<word>'. Of the <N> in-scope items in <source> at the <tier> tier, the stories cover <M>. Uncovered: <items>. Name the ones to leave out, or say 'all in'. <K> more are outside the <tier> tier — name any to pull in."* Items already `DESCOPED:` on a re-plan are not re-asked. Write `DESCOPED:` and `IN-BY-REQUEST:` lines from the reply's words; add stories for the rest; re-run the checker if stories changed; then the approval gate. Act on what comes back — more stories, or a descope the user explicitly agrees to.
- Every key link has an *owning task* — wiring mentioned nowhere is wiring that won't exist ("Chat.tsx created but nothing wires it to /api/chat" is the classic miss).
- Every truth is user-observable — "JWT library installed" is not a truth; "user can log in" is.
- Scope backstop: a story needing more than ~8 files or that can't be described in three or four checkable criteria is split, and split again, until each piece fits.

**Run the duplicate check on every unit, then present the breakdown before creating anything.** Duplicates are resolved *before* the user sees the slate (ask on related-but-different matches: extend the existing AC, or a new issue?), so approval is of the reconciled set and creation asks nothing further. Show a compact review artifact — the map (with `S<n>` ids) first where one exists, then one line per issue: `S<n> — title — labels — new | extends #N — one-line outcome`, marking which are epics/spikes and what depends on what. Enough to judge the slicing without reading full bodies. On the user's go, create the batch and report the numbers with links. Never create issues speculatively mid-discussion, and never skip the gate because the plan seems obvious.

On the user's go, create:

- **Story** — `feature` (or `bug`/`security`/`performance`/`documentation`) label plus exactly one `area:*` label, story body template: the *what*, testable acceptance criteria, and a **test plan** naming the specific automated tests that will prove it. If an AC cannot be written as something testable, the story is too vague — split it or ask; an AC that demonstrates a *failure* case ("a warning fails CI") must also say how to synthesize that failure, or execution will have to invent one; if the work genuinely can't be demonstrated by a test, the story must say so explicitly and state how it will be checked instead. **Slice vertically, not horizontally**: one story per shippable slice cut through every layer together ("show the games list end to end" beats table + endpoint + component as three stories), because only the vertical slice can be verified on its own — and per-story verification is how `/n8-verify` works. Size stories so one fits in a single working session — oversized stories are where autonomous execution stalls. Titles are outcomes phrased as verbs ("Serve the games list from the DB", not "Games API"). Every story that changes behavior gets tests in its own scope — the milestone's definition of done includes all tests passing, so untested stories are incomplete stories. Assign to the milestone. Attach as a **sub-issue of its epic**.
- **Spike** — when planning hits a question that can't be answered by asking the user or reading docs (a technology choice needing a prototype, an unknown integration), don't guess and don't stall: file a `spike`-labeled issue, time-boxed, sequenced before the stories that depend on its answer. A spike closes with a **decision comment** and follow-up stories, never with code.
- **Subtask** — `subtask` label, only where the *how* genuinely needs prescribing (specific files, patterns, gotchas, sequences). Attach as a sub-issue of its story. Don't manufacture subtasks for self-evident implementations.
- **Dependencies** — wire `blocked_by` relationships (native flags, body-line fallback per `reference/github.md`) wherever order matters; ordering lives in the graph, not in prose. Execution follows these strictly.
- **Epic AC patterns** worth using where they fit: "each child implemented *or closed with the reason it will not be*" (so an epic can complete honestly without every idea surviving); a docs/wiki-update obligation tied to children landing; an explicit "nothing here weakens the project invariants" clause. For epics with many candidate children, tier them by leverage (highest return → hygiene), one line of justification per child — it makes descoping decisions legible later.
- **Create in dependency order** (blockers before dependents) so `--blocked-by` and body cross-references carry real numbers; where a forward reference is unavoidable, fix it afterward with one `gh issue edit --body-file` pass — never leave `#TBD` behind.
- The phase list in that same PATCH reflects the final story set. Expect this to *restructure* roadmap's coarse phases — roadmap often sketches horizontal layers ("storage / commands / output") that granular planning correctly re-slices into vertical stories; note the restructuring in the description edit rather than preserving a phase list the stories no longer match.

## 4. Whole-project analysis (after all targeted milestones are planned)

Step back and analyze the full plan for what the roadmap couldn't see. Everything written here is **provisional** — marked `(provisional — after M<N>)` — unless this run planned the highest-numbered feature milestone *and* every lower one already has stories; only then is it written without the marker, and an analysis that finds no special emphases writes `emphases: none beyond the default suite` so the Audit milestone (titled `M<N>: Audit`, and never a valid explicit target) still counts as planned.

- **Specialized audits:** does the app's functionality raise specific concerns — user-generated content (security/XSS), payments (authorization), public-facing UI (508), heavy data processing (performance)? Suggest which `/n8-audit` areas deserve emphasis and record them in the Audit milestone description.
- **Project-specific skills:** would a purpose-built skill pay for itself — e.g. a "plugin-creator" skill for an app with a plugin system, a content-format skill, a deployment runbook skill? Suggest candidates and offer to build approved ones now via `/n8-skill`.
- **Gaps:** cross-milestone integration risks, missing stories, test coverage holes. Fix with the user's approval.

Log notable planning decisions to `.n8/decisions.md`.

## 5. Commit and report

Land any local state edits (`.n8/decisions.md`, CLAUDE.md invariant markings) per `reference/state.md`'s "Committing state changes" — the main ruleset blocks direct pushes.

Per milestone: story count, subtask count, dependency chains, test coverage summary. Then the analysis outcomes (audit emphases, suggested skills). Finish with the next step — more planning if milestones remain unplanned, otherwise:

> Next: run `/n8-exec M0` to execute (or `/n8-exec *` to run everything autonomously).
