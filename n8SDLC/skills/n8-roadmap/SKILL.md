# /n8-roadmap — Roadmap Planning

Turn the user's description of the app into epics and a milestone skeleton. This is deliberately coarse: epics carry acceptance criteria at the epic level only. Granular stories come later from `/n8-plan` — don't front-load that detail here.

Read `${CLAUDE_PLUGIN_ROOT}/reference/github.md` and `${CLAUDE_PLUGIN_ROOT}/reference/state.md` first. Requires `/n8-init` to have run (`.n8/config.yml` exists); if not, say so and stop.

## 1. Listen, then interrogate

The user describes the overall goal, expected features, and acceptance criteria. Ask clarifying questions until you could defend the epic list to a skeptical PM — but only about what's genuinely open: when the user's description already answers a bullet below, confirm it in your summary rather than re-asking. On a project with an earlier cycle, answers recorded then (closed epics' Notes, `.n8/decisions.md`) are confirmed in the matching batch as a quick "still true?", not asked again from scratch. A fully specified description still gets invariant confirmation, and the totalising question below whenever it fires.

**How to ask: focused batches, one topic per turn.** The roadmap is where the product gets defined, and each answer deserves the user's attention on its own. So ask in small batches of related questions, at most four and one topic each (the invariants list is the one exception: confirm it as a single batch, however many there are) (who and what success looks like; scope edges; non-functional needs; infrastructure and CI; invariants; each totalising claim), and wait for the answers before the next batch. Order the batches so an answer can change a later question. The `AskUserQuestion` tool fits when the answers are choices. You may give a recommendation inside a question, but the user's answer settles it. A recommendation nobody answered isn't a decision. This is deliberately unlike `/n8-plan`'s round one, where a long list of builder recommendations is fine, because those are mostly details the user accepts. Here, glossing over a recommendation in bulk is how a roadmap goes wrong.

**The restatement comes last, and holds no open questions.** **Before creating anything**, draft every epic's acceptance criteria, then restate every answer, asked or inferred, together with the drafted epics (title and AC) and the milestone sequence with the epics whose bulk lands in each. Send it in one message, and proceed on the user's OK; that is the confirmation, and it happens before any issue exists. Everything in it is already settled: an answer the user gave, or something the user's own description stated. Anything you decided yourself (a default, an inferred scope edge, a proposed invariant) was asked in a batch first, never slipped into the restatement for a bulk OK. The structure you build from those answers (how epics are split, their AC wording, milestone grouping and order) is proposed in the restatement itself, with a one-line reason for the order, and the OK settles it. If drafting the epics raises a new question, ask it as its own batch, then restate. Write whatever the answers changed in `.n8/config.yml` and CLAUDE.md after the OK (with a baseline, config may need nothing), before §2. Cover at minimum:

- Who uses this and what does success look like?
- Scope edges: what's explicitly *not* in v1?
- Non-functional needs that become epics or AC: auth, performance targets, accessibility (508), offline, data retention.
- **Existing delivery first.** If `.n8/config.yml` has `baseline:` (written by `/n8-map`), the infrastructure and CI answers below are already recorded: summarize them in the restatement (one line each for established, gaps and not-wanted) instead of asking, and don't re-ask what `/n8-map`'s confirmation already settled. If there's no baseline but the repo already delivers (`.github/workflows/` has files, or there's IaC or a deploy config), run `${CLAUDE_PLUGIN_ROOT}/reference/delivery-baseline.md` before the restatement. Invariant guards are classified here, once the invariants batch is answered. A proposed invariant whose guard appears in `baseline.observed-guards` (and runs in CI with a green latest run, per the reference's day-one row) is established. On the user's OK, give it its `guard: <path>` annotation in CLAUDE.md, which is how `/n8-plan` knows it's guarded. A proposed test-enforced invariant with no guard is a gap. When the restatement counts coverage ("N of M items"), M is established plus gaps, and not-wanted items don't count. Only guards whose subject already exists count; a guard for a feature that doesn't exist yet goes to that feature's epic and is named there instead. Established items are never asked about again or planned; gaps are stated in the restatement, and how to close them is `/n8-plan`'s job.
- **Infrastructure (feeds M0):** where will the application be deployed, and how? What environments exist (dev/stage/production) and where does each live? Databases, secrets, third-party services?
- **Totalising claims — ask before they become AC.** If the *user's* description says *full*, *complete*, *all*, *every*, *entire*, *comprehensive*, *any valid*, *100%*, *conformant*, *compliant*, or names a specification, first decide what the word ranges over. The test: **could `/n8-plan` write the complete list down today, from a specification, the codebase or a document, before any user data exists?**
  - **No, it ranges over runtime data** ("check every saved link", "all rows in the table", "each file in the folder"). This isn't a coverage claim: write no block and skip the question below. The AC states the behaviour over whatever set exists when the operation runs ("each bookmark in the store when `prune` runs"), and the questions worth asking are behavioural, as their own batch: the empty set, partial failures, and whether one bad item stops the run.
  - **Unclear** ("support all image formats" could mean the formats a spec defines, or whatever users upload): ask the user which they mean, as its own batch, then take the matching branch.
  - **Yes, it's the product's surface** (a specification's element set, the endpoints, the pages, the commands): ask verbatim, substituting the noun phrase that contains the trigger word for `<phrase>` and naming the tiers yourself if you know them: *"You said '<phrase>'. What do you take it to cover, and what do you explicitly not mean by it? Is that surface enumerable — a specification's element set, a list of endpoints, a set of pages? If the source has tiers (<list them, e.g. BPMN's Descriptive / Analytic / Common Executable>), which tier?"* A totalising word that first appeared in one of *your* questions counts as yours, even if the user echoed it. For a totalising word in AC *you* drafted, ask it as its own batch before the restatement, opening with *"I've written '<phrase>' as AC."* — or replace the word with the set it stands for ("dev, stage and production each deploy from CI"), never delete the quantifier without writing out its extension. When parts of a claim land in different epics, ask the tier question once per part. "Not enumerable" keeps the same block with `source: not enumerable`, `tables: n/a`, the user's concrete examples in `covers:`, and the AC states those examples in place of the word. A surface the project itself defines ("every engine operation the API exposes") records `source: this project` and `locator: <path where /n8-plan will write the list>`. Otherwise you propose the defining document, its version, a locator, and the table(s) that list the tier's elements — open the locator (context7 or a fetch) and confirm those tables exist; if the locator won't open, write `tables: unverified (proposed: <tables>) — /n8-plan confirms before enumerating`; if it opens and the tables aren't there, propose again — and the user confirms them in the pre-creation restatement. Record the answer as a fenced block, this exact shape, so `/n8-plan` and `/n8-verify` can find it:

  ```
  coverage-claim:
    claim: <the user's phrase, verbatim>
    source: <defining document, version>
    locator: <URL or path a subagent can open>
    tier: <tier, or n/a>
    tables: <the table(s) listing this tier's elements; if tier is n/a, the list that defines the surface>
    covers: <this block's share, in the user's words where possible>
    not covered: <user's words, repeated verbatim in every block of the same claim; "none — user excluded nothing">
    remainder: <the other blocks on this block's own axis — an epic block names epics, a milestone block names milestones — or none>
  ```

  It goes after the last checkbox in the acceptance criteria of every epic that delivers part of it (carried forward when the epics are created in §2) and in the description of every milestone that delivers part of it, each block carrying only its own `covers:` and naming the rest in `remainder:`. Before the restatement, list the claim's parts in the user's words and place each in exactly one block's `covers:` or in `not covered:` — a part that fits neither is a question still to ask. `/n8-verify` reads the milestone's block, so a claim due in M3 never fails at M2. Milestone descriptions carrying a block are created with `-F description=@<file>` (form in `reference/github.md`), never inline. `/n8-plan` enumerates the source at that tier and maps stories to it; the enumeration itself is planning's job — never ask the user to produce it.
- **CI (feeds the CI milestone):** GitHub Actions unless the user specifies otherwise; where do dev/stage/production deployments go and what triggers them?
- **Existing issues (projects with history).** Before drafting epics, read what's already open or was already built: `gh issue list --state open --label needs-triage --json number,title,body`, `gh issue list --state open --label bug --json number,title`, and every epic, open or closed (`gh issue list --state all --label epic --json number,title,state,body`). Then run the duplicate check from `reference/github.md` for each epic you're about to draft. Ask about them as **one batch of their own**, before the restatement: a capture that looks like a feature the user didn't describe ("#22 suggests X: part of this roadmap, or leave it?"), and an existing epic related to a new one ("extend #2's AC, or a new epic?"). For a **closed** epic, recommend a new epic marked "Related to #N", since extending it reopens verified work. When the new request reverses something an earlier epic put explicitly out of scope, name the reversal in the batch, and log it in `.n8/decisions.md` once confirmed, so it's deliberate rather than silent. A capture that clearly fits a drafted epic isn't a question. The restatement notes it under that epic ("#22 folds into epic B at planning"), because filing and triage stay with `/n8-plan`. Open bugs aren't re-planned here; the restatement counts them so the user sees what the new cycle carries.
- **Project invariants:** load-bearing constraints no story may breach without an explicit conversation — e.g. dependency policy ("zero third-party packages in the core library"), a deliberately small public API surface, warnings-as-errors, data-residency rules. Propose candidates from what you've heard; the user confirms. Keep it to a handful — ten invariants means everything is sacred, which means nothing is. Record them in the project CLAUDE.md's n8SDLC section, each marked **test-enforced** or **honor-system**: wherever an invariant is expressible as a test or build setting (package count, public API snapshot, warnings-as-errors), an executable guard gets planned into M0/CI — at roadmap granularity that means **a line in the appropriate epic's acceptance criteria** — usually infra/CI, but a guard whose subject appears later (a storage-format fixture) belongs to that later epic; `/n8-plan` places the guard story in the milestone where its subject first exists; prose rules rot, while a guard test enforces forever and makes a deliberate breach visible in the diff. `/n8-exec` treats an apparent breach as a blocker; `/n8-audit` checks the honor-system ones and hunts weakened guards. Invariants are **amendable** — but changing one is a user decision and plan drift by definition, so it's logged as an ad-hoc ledger entry and picked up by `/n8-replan`.

Record deployment/CI answers in `.n8/config.yml` under `deployment:` and `ci:` — execution must never have to re-ask.

If the context7 MCP is available (skip the check entirely when config says `context7: declined`), use it to check current documentation for any frameworks/platforms the roadmap depends on before committing to them.

## 2. Create epics

Create §3's milestones first, so each epic is created with its `--milestone` and doesn't need a second edit.

Create exactly the epics and AC the user OK'd, word for word. If you find a flaw while creating (a contradiction, a detail that belongs to `/n8-plan`), stop and show the change before creating that epic. An edit made after the OK is a decision the user never saw.

For each major capability, create one epic issue (`epic` label) using the epic body template — goal, epic-level acceptance criteria, notes. Run the duplicate check from `reference/github.md` again before each creation. Related epics were settled in the existing-issues batch; a match that appears only now (something created since) is a question for the user before creating, never a silent choice.

Cross-cutting concerns (infrastructure, CI, testing strategy) get their own epics too — they hold the M0/CI stories later. With a baseline, the infrastructure/CI epic exists only if `gaps:` is non-empty, and its AC are the gaps.

## 3. Create milestones

Lay out the milestone sequence and create each via the API (duplicate-checked):

- **M0: Infrastructure** — first. Scope from the deployment answers: environments, hosting, IaC if warranted, project plumbing.
- **CI milestone early** — usually M1: GitHub Actions pipelines for build/test/deploy to the stated targets.
- **With a baseline** these two shrink to what's missing. If `gaps:` is empty, there's no infrastructure or CI milestone at all. If there are gaps, there's one milestone, `M<n>: Infrastructure & CI gaps`, first in the sequence, whose phases are the gaps and nothing else. **Numbering:** with no existing milestones, it's `M0`, and features start at `M1`. When the repo already has `M<N>:` milestones, open or closed (an earlier n8SDLC cycle), numbering continues after the highest, because skills match milestones by prefix and a second `M0:` collides with the first. Its description names the baseline (`baseline: checked <date> @ <sha>`, in `.n8/config.yml`) so `/n8-plan` carries the established items as `ESTABLISHED:` lines. Put the choice in the restatement: "Your delivery already covers N of M items (listed), so M0 holds only the K gaps", or "…so there's no M0 or CI milestone".
- **Feature milestones** — group epics into coherent, shippable increments. Order by dependency and value.
- **M<N>: Audit** — always last: audit passes (`/n8-audit`) and approved finding fixes. It gets **no epic of its own** — audit findings attach to the epics they concern, or stand alone.

Every milestone description carries: goal; ordered phases (the epics' work in the order it lands, at epic granularity — `/n8-plan` re-slices them into stories; for the Audit milestone, the audit areas in order); the `coverage-claim` block for whatever this milestone delivers of a totalising claim; and definition of done (all issues closed, all tests passing, `/n8-verify` passed). Assign each epic to the milestone where the bulk of its work lands (stories get individually assigned during `/n8-plan`).

## 4. Commit and report

Append a `## /n8-roadmap — <date>` section to `.n8/decisions.md` naming the choices made (spec version, tiers, ordering, what was deferred), then land the run's state edits (`.n8/`, CLAUDE.md) per `reference/state.md`'s "Committing state changes" — a `n8/roadmap-state` branch and PR, since the ruleset blocks direct pushes to main.

Summarize: the epic list (numbers + titles), the milestone sequence with one-line goals, the recorded deployment/CI answers, and any open questions deferred to milestone planning. Say that the first milestone this run created is planned first, whatever its number (`M0` on a fresh project; the gaps milestone when there is one; otherwise the first feature milestone), and that `/n8-plan *` plans everything, then end:

> ➡ Next: /n8-plan M0

**End on the Next line.** The reply's final line is `➡ Next: /n8-plan M0` (an example — substitute the real command and arguments): one recommended command, alone on the line, nothing after it. The why and any alternatives go in the sentence above it, never appended to it. Claude Code's prompt suggestion reads the transcript; a bare, final, unambiguous command is what lets the user accept it with Tab.
