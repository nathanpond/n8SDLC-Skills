# /n8-verify — Milestone Verification

Verification is part of done: `/n8-exec` merges code, but only a passed verification closes a milestone. An AC that "should" pass isn't verified until it's been exercised.

**Verify in a fresh context.** The session that executed the milestone is the one reader that cannot check it — it inherits the assumptions that produced the code, so "be adversarial" is not a remedy. Run from the project directory. `R=$(gh repo view --json nameWithOwner --jq .nameWithOwner)`; pass `-R $R` on every `gh` command. Two different numbers: `M` is the milestone index from the title (`M2:` → `M=2`, used in the branch prefix `milestone/m$M-`), `N` is GitHub's milestone number — not the same, and the default listing omits closed ones. Resolve `N` with a one-match assertion and never hand-type it:

```sh
M=2
N=$(gh api "repos/$R/milestones?state=all&per_page=100" --jq "[.[] | select(.title|startswith(\"M$M:\"))] | if length==1 then .[0].number else error(\"expected one M$M: milestone, got \(length)\") end")
```

Stories are every issue in the milestone that is not an epic, spike, subtask or PR — `gh api "repos/$R/issues?milestone=$N&state=all&per_page=100" --paginate --jq '.[] | select(.pull_request|not) | select(any(.labels[].name; IN("epic","spike","subtask")) | not) | .number'`, one number per line (an array-wrapping filter emits one array *per page*, and `inside()` would test the whole label set and pass every issue that also carries `area:*`) — never the epics' sub-issue lists, which miss audit findings and the bugs this skill itself files. An open `bug` already carrying `sev:medium` or `sev:low` is a carried bug: report it, don't verify it. Each story's epic (`gh api repos/$R/issues/<n>/parent --jq .number 2>/dev/null || echo none`) says where its record goes; on a re-verify, a story is skipped only if its record destination — the epic, the PR, or the issue itself — already carries a record comment naming its number. The commit to verify against is the `mergeCommit.oid` of the highest-numbered milestone PR; run the suite in a worktree at that commit. The stack file is `${CLAUDE_PLUGIN_ROOT}/reference/stacks/<stack>.md` for the `stack:` in `.n8/config.yml`; it names the runner and each test directory. Per story, spawn a `general-purpose` subagent (**never `fork`**) whose prompt carries the issue number, `$R`, that commit and worktree, the runner and test directories, and — pasted, since it cannot read this file — the §2 checks, the VERIFIED/ORPHANED/STUB/MISSING vocabulary, "ignore the `[x]` state of the boxes and every closing comment", "post nothing, edit nothing", and the required return: an AC-by-AC table with evidence per row, a complement column, and one claim with the exact command to re-run it. Under `--auto` it exercises; under `--testplan`, or for any AC on the can't-verify list below, it prepares the environment and returns the UAT steps for *you* to walk with the user — a subagent cannot hold that conversation. You collate, re-run one claim per story yourself, run the full suite once, and post the record.

Read `${CLAUDE_PLUGIN_ROOT}/reference/github.md` and `${CLAUDE_PLUGIN_ROOT}/reference/state.md`.

## 1. Resolve targets and mode

- Targets like `/n8-exec`: `M1`, `M1,M2`, `*`. No argument → every open milestone with a merged PR — `gh pr list --state merged --search "head:milestone/m$M-" --json number,headRefName,mergeCommit` non-empty (server-side search; a `--limit` form drops older PRs silently). When that returns more than one PR, milestone-level records and waivers go on the **highest-numbered** one, and its merge commit is the one verified against. A milestone named explicitly that is already closed is re-verified, and reopened first if it fails. Bugs this verification files stay in the same milestone, so "stories closed" is deliberately *not* the predicate — a re-run must still find them.
- A milestone with no merged PR hasn't been executed — say so and stop for that target.
- Modes: `--auto` = verify everything the agent can itself (default when the user just runs `/n8-verify`); `--testplan` = produce step-by-step manual test plans for the user to run instead.

## 2. Verify (per milestone)

Work story by story against acceptance criteria — the AC checkboxes are the contract. **Do not trust closing comments or summaries: they document what the executor *said* it did. You verify what actually exists.**

- **The existence ladder is the floor, not the check.** *exists → substantive → wired* answers whether an artifact is there; it cannot distinguish code that works from code that does the thing unconditionally. For every AC whose correctness depends on something *not* happening — a cancellation, a refusal, a scope boundary, a supersession — assert the complement too, and treat its absence from the story's tests as a verification failure worth a bug, not a pass. Detect it mechanically: locate the story's tests by the must-have artifacts' basenames (`OidcSignInService` → `OidcSignInServiceTests.cs`) and by case-insensitive stems of the plan's words with separators stripped (`grep -rli 'roleassignment' <test dir>` finds `RoleAssignments` where `role_assignments` does not), then `grep -niE 'assert\.?(false|empty|throws|raises|equal\(0|null|notequal|doesnotcontain|notcontain|isfalse|isnull|isempty|areequal\(0)|Is\.(False|Empty|Null)|\.not\.|toBe(Null|Falsy|Undefined)|toThrow|toHaveLength\(0\)|toHaveBeenCalledTimes\(0\)|pytest\.raises|assert +not |is None|DidNotReceive|Never\(?\)?|assertRaises|assertFalse|Should\(\)\.(BeFalse|BeEmpty|BeNull|NotContain|Throw|HaveCount\(0\))'` — xUnit, NUnit, MSTest, jest/vitest, pytest, Moq, FluentAssertions; extend it in the stack file for others — the grep **screens**; a hit is read to confirm it asserts *this* AC's complement, and a miss is read for a positive assertion over a complete set (`executedPath == ["A"]`, or a `BadRequest` status on the rejection path). Only after the read: neither present means the complement is unasserted.
- **Verify the milestone's `## Outcomes` as truths.** `/n8-plan` writes five to ten user-observable outcomes in the milestone description, each `→ #<issue>`; verify each the way a must-have truth is verified — exercised, with evidence — regardless of whether its story's AC passed, because a story can close with every box ticked while the outcome it was for does not hold. An outcome that does not hold is a failure filed against its story.
- **Check the milestone's coverage claim, not just its stories.** If the milestone description carries an enumerated surface and coverage map from `/n8-plan`, verify the map against what actually shipped — the map exists so a later reader can check the claim rather than trust it, and you are that reader. Read it with `gh api repos/$R/milestones/<number> --jq .description` — the milestone's `number` from `gh api repos/$R/milestones`, not its `id`, which 404s. The map is whatever structure resolves every enumerated *item* — an element of the coverage claim's source — to an issue number: `<item> → #<issue>` lines or a table with an issue column, plus any `OUT-OF-TIER:`/`DESCOPED:`/`IN-BY-REQUEST:` lines. A phase list resolves phases, not items, and is not a map even when every phase cites issues. A row deferred to another milestone without a `DESCOPED:` line carrying the user's words is a finding. An item is covered when its owning story's row in this record is all-VERIFIED; a `DESCOPED:` or `IN-BY-REQUEST:` line is covered only if it carries the user's quoted words, otherwise it is a finding; an `ESTABLISHED:` line is covered only if its evidence command, re-run now, still passes (a regression in delivery that already existed is a finding, just as a regression in new work is); an `OUT-OF-TIER:` or `REMAINDER:` line is covered by construction — it exists so the omission is visible against the roadmap's coverage claim. If the milestone's title *or the first line of its description* makes a totalising claim ("full", "complete", "all", "every", "conformant") and no map exists, that is a finding too, unless the word ranges over runtime data ("prune every dead link"), which `/n8-roadmap` records as behaviour over each item present at run time, not as a claim. For those, verify the AC instead, including the empty set. **Findings block closure** until the user waives them in a comment on the milestone's PR — an unverifiable completeness claim closing a milestone is the false green this skill exists to stop.
- **Cash the must-haves block first.** For each artifact it names, check three levels: *exists* → *substantive* (real implementation, not a stub — grep for `TODO|FIXME|placeholder|not implemented`, empty returns, missing exports) → *wired* (imported somewhere else AND referenced beyond the import line — or *registered*, where the codebase wires by DI container, plugin registry or string-keyed factory: an unimported handler a registry loads is VERIFIED, not ORPHANED). A `TODO` inside working code is not a stub; a stub is a body that doesn't do what its name claims. Classify each: exists+substantive+wired = **VERIFIED**; unwired = **ORPHANED**; not substantive = **STUB**; absent = **MISSING**. Anything below VERIFIED fails its truth.
- **The verification record is a comment on each epic that has a story in this milestone**, carrying only that epic's stories: the truth table plus the evidence summary, posted before closing anything. Milestone-level findings (coverage, completeness) go on the milestone's PR. It's what a future session reads to know verification actually happened. Issues with no epic (audit-filed findings, quick captures) get their record on the milestone's PR — or on the issue itself when there's no PR. Issues without a must-haves block (audit findings) get their checks derived from AC, same as `--auto` does for Demo-less stories.
- For AC whose proof *is* a CI/deploy run (workflow gates, release paths): a run's `conclusion` is the workflow's self-report — `success` on a job that ran zero tests. Re-fetch it fresh (`gh run view <id> -R $R --json conclusion,headSha`) **and** read the gate lines of the job log (`gh run view <id> -R $R --log | grep -E 'dotnet test|Passed!|Failed!|Total tests|Tests:|passed in'` — the full log runs to thousands of lines) to confirm the gate step actually ran against the commit in question. Recreate red/green runs only when the history is absent or ambiguous.
- Run the full automated test suite; confirm the tests each story's test plan promised actually exist and pass. A green suite with missing promised tests is a failure.
- **A changed snapshot/golden is a claim, not a result.** If any snapshot, golden file, or recorded baseline was updated during execution, review the diff and confirm the new output is *correct* — a golden regenerated to make a test pass proves nothing. The verification record must say why the new output is right.
- **--auto:** exercise each AC directly where possible — run the app, hit the endpoints, drive the UI, inspect outputs. Prefer evidence over inspection: "I called it and observed X" beats "the code looks right". Where a story has no `Demo` (agent-verifiable by design), derive the checks from its AC and must-have truths.
- **--testplan:** produce manual test scenarios and run the UAT protocol below.

**Steps the agent can't verify** (real devices, third-party dashboards, payments, emails, deployment targets you can't reach): even under `--auto`, don't pretend — run the UAT protocol below on those steps. Milestone closure waits for the user's results.

## The UAT protocol (manual steps and --testplan)

The user performs UAT — **you prepare the environment and give instructions; you must not run the demo yourself and report the results back** (that's automated verification wearing a costume). Start whatever needs starting *before* handing over — dev server up, seed data in, URL ready.

- Build scenarios from each story's `Demo` script where one exists; derive from AC otherwise. Order them **by user journey, not by story or component**.
- One test at a time, plain conversational text: here's what should happen — does it? "yes"/"next" passes. Anything else is logged as a failure with **severity inferred from the user's own words** (crash/broken/fails → blocker; doesn't work/wrong/missing → major; slow/weird/minor → minor; spacing/color → cosmetic) — never ask them to rate severity.
- **Never fix during testing.** Log everything, finish the pass, then diagnose — mid-UAT fixes invalidate the session and lose findings.
- Internal changes get summarized verification with its scope stated — "47 tests in `api/`, UI untested" — never a bare count; the user checks what they'd encounter in normal use, not your source code.

## 3. Failures → bugs, offer re-exec

For each failed AC or defect found:

1. Duplicate-check, then file a `bug` issue in the **same milestone**, referencing the story, labelled `sev:*` — UAT words map blocker→`sev:critical`, major→`sev:high`, minor→`sev:medium`, cosmetic→`sev:low`. If you reproduced it, add `confirmed` and include repro steps — a **missing complement test is `confirmed` and `sev:high`** (its absence is reproducible, and the unguarded behaviour is what ships), so it blocks closure.
2. Attach it as a sub-issue of the relevant story's epic.

Then offer to run a fix pass immediately (`/n8-exec` scoped to the new bugs on a fix branch). The milestone stays open until a re-verify passes.

## 4. Close and report

A milestone passes when: every AC is verified (agent-verified or user-approved manual steps), promised tests exist and pass, no open `confirmed` bug at `sev:critical`, `sev:high` or with no severity label remains in it, and no coverage or completeness finding is open (waived findings carry the user's comment). Confirmed `sev:medium` and `sev:low` bugs may be carried: they stay in this milestone (so a re-run still finds them), the gate ignores them, and the report lists each. An epic whose AC the verification proved closes even with carried medium/low children — the children keep their own issues — so a closed milestone never drags its epic behind it. Then close the milestone (`gh api -X PATCH repos/$R/milestones/$N -f state=closed`). The blocking-bug check uses `$N` from the resolution above (a hand-typed number can name the wrong milestone and read as clean): `gh api "repos/$R/issues?milestone=$N&labels=confirmed&state=open&per_page=100" --jq '[.[] | select(any(.labels[].name; IN("sev:critical","sev:high")) or (any(.labels[].name; startswith("sev:")) | not))] | length'` must print 0 — `confirmed` with no severity label blocks — this skill always files with a `sev:*`, but `/n8-file` and hand-filed bugs often don't, and an unrated confirmed bug is not known to be minor. A `sev:high` the user chooses to defer is relabelled `sev:medium` with the user's words in a comment — the gate reads labels, not intent. Reopen a closed milestone before re-verifying with `gh api -X PATCH repos/$R/milestones/$N -f state=open`.

**Epics close here too:** an epic whose epic-level AC the verification just proved gets its AC boxes ticked and is closed with the verification record as its closing evidence. An epic with unfinished *stories* in later milestones stays open; carried medium/low bugs do not hold it.

When a closed milestone represents shippable value (feature milestones especially, and always the final one), **suggest `/n8-release`** — it handles version selection, tagging the verified commit on main, generated notes, and whatever the tag triggers (production deploy, publish). Never release unasked; the suggestion is the offer.

Report per milestone: verified AC count, evidence highlights, manual steps awaiting the user (if any), bugs filed, closed or still open and why — honestly; a milestone that limps through is reported as such. Pick the single next step — a fix pass (`/n8-exec` on the milestone with filed bugs), remaining verifications, `/n8-release` when the closed milestone is shippable, the next `/n8-exec`, or `/n8-audit` if all feature milestones are done — and end:

For token efficiency before the next phase, suggest clearing context:

> ➡ Next: /clear

Then: `/n8-exec M2` (or `/n8-release` if milestone is closed and shippable)

**End on the Next line.** The reply's final line is `➡ Next: /clear` (or the direct next step if running single milestone without context concern): one recommended command, alone on the line, nothing after it. The why and any alternatives go in the sentence above it, never appended to it. Claude Code's prompt suggestion reads the transcript; a bare, final, unambiguous command is what lets the user accept it with Tab. For automated multi-milestone orchestration, use `/n8-workflow M0,M1,M2` instead, which handles exec→verify→retry loops with automatic clearing.
